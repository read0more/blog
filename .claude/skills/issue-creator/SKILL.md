# GitHub issue 작성

## 1. 먼저 확인한다

- `gh issue list --state all --limit 15`로 같은 주제의 이슈가 있는지 본다. 열린 이슈가 있으면 새로 만들지 않고 그 이슈에 댓글을 단다(5번).
- 이어지는 작업이면 앞선 이슈·PR을 본문에서 `#번호`로 참조한다(예: `#32 / #33의 개별 포스트 번역 지원을 확장하여`).
- 저장소 제약(정적 export, draft 규칙, basePath)은 `CLAUDE.md`에 있다. 범위를 쓰기 전에 관련 부분을 읽는다.

## 2. 제목

`<type>: <무엇을 하는지>`

- type은 커밋 컨벤션과 같다: `feat` `fix` `refactor` `docs` `chore` `test` `style`.
- 결과를 명사형으로 끝낸다. 마침표·이모지·대괄호 태그를 쓰지 않는다.
- 좋은 예: `feat: 본문에서 실행되는 라이브 코드 블록`, `feat: 번역된 글만 제공하는 영어 사이트 지원`, `refactor: 포스트 카테고리를 디렉토리 기반으로 전환`

## 3. 본문 양식

섹션 이름을 바꾸지 않는다. 내용이 없는 섹션은 통째로 뺀다(배경·범위는 필수).

```markdown
## 배경

<왜 필요한지 1~3문장. 무엇이 불편했는지, 무엇을 하려다 막혔는지. 해결책은 여기 쓰지 않는다.>

## 범위

- <결정된 동작을 확인 가능한 형태로: URL, 파일 위치, 마크다운 문법, 프론트매터 키, 실패 시 동작(빌드 오류 등)>
- <기존 동작 중 유지할 것>
- 이번 범위에 포함하지 않는다: <뺀 것>

## 완료 기준

- <검증 가능한 문장. "잘 동작한다"가 아니라 무엇이 되고 무엇이 유지되는지>
- 린트·타입·포맷·빌드·E2E와 GitHub CI를 통과하고 PR에서 이 이슈를 연결한다.
```

## 4. 중요하게 다룰 내용

- **범위에는 결정을 쓴다.** 함수명 같은 구현 세부는 PR 몫이다. 이슈에는 독자·작성자 입장에서 보이는 동작과 규칙을 쓴다.
- 해당될 때 이 저장소의 제약을 짚는다.
  - GitHub Pages 정적 배포: `output: export`, `trailingSlash`. 서버·middleware·redirect를 쓰지 않는다.
  - `BASE_PATH=/blog` 하위 경로에서 동작하는지, 직접 접근·새로고침이 되는지
  - draft 규칙: `OMIT_DRAFTS=true`인 배포 빌드에서만 제외한다. 공개 글·태그·번역이 0개여도 빌드가 성공해야 한다.
  - 기존 글 URL이 바뀌는지
- 기능 추가(`feat`)라면 실제 글 맥락에서 확인할 `draft: true` 데모 글을 범위에 넣는다.
- **화면에 새 문구가 생기면 영어 번역을 범위에 넣는다.** 버튼·라벨·안내·`aria-label`처럼 글마다 공통으로 붙는 UI 문구가 대상이다(예: 라이브 코드 블록의 `코드 + 미리보기` / `미리보기` / `코드` 버튼). 범위에 새 문구의 한국어와 영어를 함께 적고, `messages/ko.json`·`messages/en.json` 양쪽에 같은 키로 추가한다고 쓴다. 컴포넌트에 문구를 직접 쓰지 않는다. 키가 한쪽에만 있으면 `npm run check:messages`가 빌드를 막는다.

## 5. 계획이 바뀌면 댓글로 남긴다

본문을 조용히 고치지 않는다. `gh issue comment <번호> --body-file <파일>`로 남긴다.

- 작은 추가: `범위 추가: <내용>. 같은 PR(#N)에 포함.`
- 방향 변경: `## 구현 계획 수정: <요지>` 아래에 번호나 불릿으로 바뀐 점을 쓴다.

## 6. 문체

- 하다체(`~한다`, `~이다`)로 쓴다. 합니다체와 섞지 않는다.
- em/en dash를 쓰지 않는다. 콜론·가운뎃점으로 대신하거나 문장을 바꾼다.
- 불릿 하나에 사실 하나. 코드·경로·명령은 백틱으로 감싼다.
- "효율적으로", "다양한", "개선" 같은 빈 수식어 대신 구체적인 값이나 동작을 쓴다.

## 7. 생성

1. 본문을 `mktemp`로 만든 임시 파일에 쓴다. 셸 따옴표 안에 넣으면 백틱과 `$`가 깨진다.
2. `grep -n '[—–―]' <파일>`이 0건인지 확인한다.
3. `gh issue create --title "<제목>" --body-file <파일>`. 라벨·assignee는 붙이지 않는다(기존 관례).
4. 생성을 요청받았으면 바로 만들고 이슈 URL을 알린다. 초안만 요청받았으면 제목과 본문을 출력하고 끝낸다.
