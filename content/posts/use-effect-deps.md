## 의존성 배열은 "캐시 키"다

useEffect의 두 번째 인자는 "언제 다시 실행할지"를 결정하는 캐시 키다. 배열 안의 값이 이전 렌더와 하나라도 다르면 React는 정리(cleanup) 함수를 호출한 뒤 effect를 다시 실행한다. 그래서 의존성을 "effect가 실제로 읽는 값"과 정확히 일치시키는 것이 전부다.

```jsx
useEffect(() => {
  const id = setInterval(() => setCount(c => c + 1), 1000);
  return () => clearInterval(id);
}, []);
```

위 코드는 의도적으로 빈 배열을 쓴다. 함수형 업데이트(c => c + 1)를 사용했기 때문에 effect는 count를 직접 읽지 않는다. 읽지 않는 값은 의존성에 넣지 않는다 — 이 원칙만 지켜도 대부분의 버그가 사라진다.

## 흔한 실수: 객체와 함수를 그대로 넣기

가장 잦은 실수는 매 렌더마다 새로 만들어지는 객체나 함수를 의존성에 넣는 것이다. 참조가 매번 바뀌므로 effect가 끝없이 다시 실행된다.

```jsx
// 매 렌더마다 options가 새 객체 → effect가 계속 재실행
const options = { headers: { token } };
useEffect(() => {
  fetchUser(options);
}, [options]);
```

해결책은 두 가지다. 객체를 effect 안으로 옮기거나, 원시 값(token)만 의존성에 넣는 것이다. 대부분의 경우 후자가 더 단순하고 정확하다.

### useCallback이 항상 답은 아니다

함수를 의존성으로 넘겨야 한다면 useCallback으로 참조를 고정할 수 있다. 하지만 useCallback 자체도 의존성을 가지므로, 근본 원인을 옮기지 않고 메모이제이션만 덧대면 복잡도만 늘어난다. 먼저 "이 값을 정말 의존성에 넣어야 하나"를 물어라.

## 정리: 세 가지 규칙

- effect가 읽는 값만 의존성에 넣는다.
- 참조가 매번 바뀌는 객체·함수는 effect 안으로 옮긴다.
- 상태 갱신은 가능하면 함수형 업데이트로 바꿔 의존성을 줄인다.

> 의존성 배열은 "최적화"가 아니라 "정확성"의 도구다. 비우거나 채우는 기준은 성능이 아니라, effect가 무엇을 읽는가다.
