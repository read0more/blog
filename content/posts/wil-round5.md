이번 주 질문은 "어떤 상태 라이브러리를 쓸까"가 아니라 "**이 상태의 원본은 어디에 있나**"였다. 서버가 원본인 값(TanStack Query)·URL이 원본인 값(nuqs)·클라이언트가 원본인 값(Zustand)을 먼저 가른 뒤에야 라이브러리를 골랐다.

## 🧠 이번 주에 새로 배운 것

이번 과제의 목표는 단순히 라이브러리 사용법이 아니라, **코드를 짜기 전에 화면의 상태를 먼저 분류하는 것**이었다.

- **코드보다 "상태 분류표"가 먼저.** 화면에 필요한 상태를 `상태 · 소유자(원본) · 수명 · 공유 범위 · 선택 이유`로 먼저 표에 적고 나서 도구를 골랐다. 질문이 "무슨 라이브러리를 쓸까"가 아니라 "이 값의 **원본이 어디냐**"로 바뀌니, 서버 원본을 Zustand에 복사하거나 URL이 원본이어야 할 조건을 컴포넌트 state에 가두는 선택이 애초에 후보에서 빠졌다. **도구는 원본을 정한 뒤에 따라왔다.**
- **서버 원본 → TanStack Query.** 목록은 서버가 원본이고 조건 변경·페이지네이션 인터랙션이 있어 캐시·재요청·로딩/에러를 위임했다. `queryOptions` 팩토리로 query key·queryFn·캐시 정책(`staleTime`/`gcTime`)을 한곳에 묶으니, 클라이언트 `useQuery`와 서버 `prefetchQuery`가 **같은 정의**를 재사용했고 조건은 그대로 query key·요청에 실려 어긋나지 않았다.
- **URL 원본 → nuqs / 클라이언트 원본 → Zustand.** 공유·새로고침·앞뒤 이동으로 복원돼야 하는 목록 조건(q·category·sort·page)은 원본이 URL이라 nuqs `useQueryStates`로 **타입 있는 URL 상태**로 뒀다. 서버 원본이 없는 익명 장바구니·위시리스트는 클라이언트가 원본이라 Zustand에 상품 id `Set`만 저장하고, 헤더 개수는 저장하지 않고 `.size`로 **파생**했다.

## 💭 고민 점들

- **nuqs와 TanStack Query를 함께 쓰는 구조.** 조건의 원본은 URL(nuqs)이고, 그 조건이 그대로 query key로 흘러들어가 서버 요청이 된다. URL을 바꾸면 → key가 바뀌고 → `useQuery`가 재요청하는 단방향 흐름으로 짜, 두 라이브러리가 같은 조건 하나를 가리키게 하는 게 고민의 핵심이었다.
- **nuqs의 CSR bailout과 prefetch TTFB — 둘 다 `<Suspense>`지만 목적이 다르다.** `useSearchParams`를 쓰는 필터를 Suspense로 감싸지 않으면 정적 프리렌더에서 CSR bailout 빌드 에러가 난다(layout에서 격리). 이와 별개로 서버 prefetch(`await`)를 page에서 바로 하면 그게 끝날 때까지 첫 응답(TTFB)이 통째로 지연되는데, prefetch를 Suspense 경계 **안**으로 밀어 넣어 헤더·필터 shell을 먼저 스트리밍하고 목록만 뒤따르게 했다. 같은 `<Suspense>`인데 하나는 **bailout 격리**, 하나는 **스트리밍 경계**다.

## 🤔 놓친 것 — 대안이 요구사항을 건너뛴 경우

홈 데이터를 **React Server Component에서 직접 fetch**하도록 구현하였다. 인터랙션이 없는 홈에선 클라이언트 구독을 걷어내고 서버에서 조회하는 편이 낫지 않을까 생각해서 선택한 부분이었다.

문제는 이번 필수 요구사항이 "홈·목록 **각각** queryOptions 팩토리를 만들어 key·queryFn·캐시 정책을 한곳에서 재사용"이었다는 점이다. 홈을 RSC 직접 fetch로 돌리면서 나는 **홈 queryOptions 팩토리 자체를 지워버렸고**, 결과물이 요구한 산출물과 어긋났다. 개념적으로 괜찮은 대안이 될 수 있는 선택이더라도 **요구사항을 제대로 읽지 못하면**, 증명해야 할 것을 증명하지 못한 채 다시 만들어야 하는 경우가 생긴다.

배운 것: 이건 과제라서가 아니라 실무였어도 똑같이 문제다. 대안 자체는 괜찮을 수 있어도, **명세를 제대로 이해하지 못해 결과물이 명세와 달라지면 그 어긋남 자체가 문제**다. 요구사항을 정확히 읽고, 선택을 바꿔야 한다면 공유하여 의견을 묻고 합의해 정하는 게 먼저다.
