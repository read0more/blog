이번이 벌써 루프팩을 시작한 지 8주차다. 이번엔 테스트에 관한 과제였다. 실무에서 테스트를 작성한 적이 없었기 때문에 관심이 많은 주제였다. 전제는 전주까지 진행한 과제 코드를 대상으로 테스트한다는 것이었고, 프론트엔드는 지켜야 할 스펙이 어디에도 적혀 있지 않으니 무엇을 어떻게 검증할지 먼저 정하고 그것만 테스트로 작성하는 방식이었다.

시작 전에 한참 헤맨 지점이 있었다. 예전부터 감이 잘 안 잡히던 부분인데, "구현 세부사항이 아니라 사용자 행위를 테스트하라"이다. 구현 세부사항에 대해서 애매한 이미지만 있고 제대로 구분하지 못했다. CSS 클래스 테스트가 안티패턴인 건 테스트가 깨지기 쉬우니까 그런 건가? 그러면 `getByRole('button', { name: '장바구니 담기' })` 이런 식으로 버튼 텍스트를 가져오는 것도 안티패턴 아닌가? 와 같은 고민들이었다. 하지만 Kent C. Dodds의 [Testing Implementation Details](https://kentcdodds.com/blog/testing-implementation-details) 글을 읽고 나서야 조금 정리가 됐다. 

결론부터 말하자면 글을 읽고 나서는 버튼명은 사용자가 실제로 보는 것이라, 그게 바뀌면 테스트도 같이 바뀌는 게 맞다고 판단했다. 모두가 동의하는 방식은 아니라고 Kent가 글에서도 밝히지만, "사용자가 보고·듣고·행하는 것을 테스트하라"는 그 관점이 내가 헷갈리던 부분을 명확하게 해주었고 충분히 납득이 가는 부분이라고 생각했다.

또 알게 된 것은 "사용자"는 사이트를 쓰는 end user만이 아니었다. **컴포넌트를 쓰는 개발자**도 사용자다. end user는 렌더된 결과를 보고 상호작용하고, 개발자 사용자는 props를 보고 상호작용한다. 그래서 보통 전달된 props와 렌더 결과를 테스트하고, state는 테스트하지 않는다. state를 테스트하기 시작하면 이 두 사용자와도 다른 방식으로 앱을 쓰는 "세 번째 사용자", 즉 테스트 자신이 생겨난다. 앱을 검증하려고 만든 테스트에 앱이 거꾸로 묶여버려, 정작 앱은 멀쩡한데 테스트가 깨지는 false negative가 난다. Kent의 문장 하나가 기준이 됐다. "테스트가 소프트웨어가 실제로 쓰이는 방식을 닮을수록, 그 테스트가 주는 확신도 커진다." 테스트를 작성할 때의 결정은 모두 이 원칙을 두고 내렸다.

## 0단계: 환경을 나누고 모킹 경계를 세우기

0단계는 먼저 환경과 모킹 경계부터 세우는 부분이었다. 환경 세팅과, 기존 테스트가 새 설정에서 안 깨지게 손보는 반복 작업은 AI에게 맡겼다. 대신 모킹 경계를 어디에 둘지는 직접 정했다. 그게 곧 무엇을 지킬지를 정하는 결정이라서다.

환경부터 나눴다. 전역 기본은 `node`(`vitest.config.ts`의 `environment: "node"`)로 두고, DOM이 필요한 파일에만 첫 줄에 `// @vitest-environment jsdom` pragma를 달아 개별 지정했다. 나의 경우 jsdom으로 돌아야 하는 테스트 파일은 컴포넌트·클라이언트 훅 테스트 6개뿐이고, 나머지는 node에서 돌려도 되는 상태였다.

그러면 왜 굳이 나눠야 할까? 이유는 단순했다. `render()`는 내부에서 `document.createElement`를 부르니 DOM 환경이 있어야 한다. 반면 순수 로직이나 route 핸들러 테스트는 `render()`를 안 쓰니 `document`를 건드릴 일이 없고, node로 충분하며 더 빠르다. 전역을 통째로 jsdom으로 깔면 DOM을 안 쓰는 파일까지 매번 가짜 DOM 트리를 세우는 비용을 낸다.

이 비용을 확인하기 위해 14파일 기준으로 분리했을 때와 전부 jsdom으로 돌렸을 때의 `vitest run` 출력을 비교했다.

| 항목 | 분리 (node + jsdom 6) | 전부 jsdom (14) | 배율 |
| --- | --- | --- | --- |
| transform | 1.08s | 2.01s | 1.9배 |
| setup | 3.61s | 8.25s | 2.3배 |
| import | 1.62s | 2.95s | 1.8배 |
| tests | 1.30s | 2.82s | 2.2배 |
| **environment (환경 셋업)** | **4.31s** | **20.87s** | **4.8배** |
| Duration | 2.08s | 5.97s | 2.9배 |

`environment` 항목이 4.31초에서 20.87초로, 약 4.8배 뛴다. DOM을 안 쓰는 8개 파일까지 브라우저 흉내 환경을 세운 비용이다. 14파일 시점에 이미 환경 셋업에서만 16초 넘게 차이가 나고, 이 비용은 파일 수에 비례해 쌓일 것이다.

### 네트워크 모킹 경계의 변경

다음은 모킹 경계였다. 네트워크가 나가는 부분은 MSW를 추가해 가로채게 변경하였다. 또한, `onUnhandledRequest: "error"`로 **모킹되지 않은 요청은 조용히 나가지 못하게** 막았다. 정의하지 않은 요청은 즉시 실패한다.

나의 원래 코드엔 `vi.mock("@/entities/product/api/fetchProducts")`로 밖으로 보내는 요청이 있는 함수 자체를 모킹했는데, 이 방식에는 문제가 있었다. API 부분만 모킹하는 게 아니라 함수 자체를 모킹했기 때문에 함수 내의 코드가 아예 실행되지 않는다는 점이었다. 나는 API 응답만 테스트에 맞게 바꿔서 테스트하고 싶은 건데 사실상 다른 함수를 테스트하게 변한 것이다. 이는 위에서도 언급한 "세 번째 사용자", 즉 테스트 자신이 생겨버린 것이다.

하지만 이젠 MSW를 이용해 요청을 가로채서 함수의 동작은 그대로 두고 응답만 바꾸는 게 가능해졌다. 이로 인해 테스트가 실제로 쓰이는 방식과 훨씬 닮게 되었다.

### 비용이 큰 E2E 테스트는 어디에?
E2E를 어느 명령에 넣을지도 정해야 했다. 별도 명령으로 빼지 않고 `pnpm test`(`vitest run && playwright test`) 안에 넣어 뒀다. 이 레포에서 `pnpm test`는 pre-push에서만 돌게 해뒀는데, 이는 예전 주차에서 했던 결정이다. 이런 판단을 내린 이유는 커밋은 자주 해도 push는 그만큼 자주 하지 않으며, E2E가 무거워도 매 push에 한 번 도는 비용은 감수할 만하다고 생각했다. 게다가 push하는 순간 그 코드가 다른 작업자에게도 노출되니 더더욱.

## 1단계: 무엇을 어디서 검증할지 정하기

1단계는 과제에서 지정된 15개 항목을 단위·통합·E2E 중 어디에 배치할지 정하고 그 근거를 적는 일이었다. 아래는 그 15개에 대한 테이블이다. 내가 내린 결정은 단위 6개, 통합 8개, E2E 4개였다. 이 배치와 애매판단, 그리고 셋업 시간 같은 수치 측정은 전부 직접 했다. AI에게 구현을 넘기기 전에 무엇을 어떻게 할지를 내 판단으로 정하는 단계였다.

| # | 검증 대상 | 방법론 |
| --- | --- | --- |
| 1 | 개수 파생 | 단위 |
| 2 | URL 조건 → query key | 단위 |
| 3-1 | `buildProductListSearchParams` | 단위 |
| 3-2 | `clampPageToLowerBound` | 단위 |
| 3-3 | `buildProductListTitle` | 단위 |
| 3-4 | `isServerError` | 단위 |
| 4 | 목록 로딩 → 성공 | 통합 |
| 5 | 목록 빈 결과 | 통합 |
| 6 | 목록 에러 (5xx 경계 / 4xx 인라인) | 통합 |
| 7 | 에러에서 재시도로 복구 | 통합 |
| 8 | 카테고리 변경 → 목록 변경 | 통합 |
| 9 | 정렬 변경 → 순서 변경 | 통합 |
| 10 | 페이지 이동 → 목록 변경 | 통합 |
| 11 | 조작이 URL 반영 · URL로 재진입 | E2E |
| 12 | 담기 → 헤더 개수 · 다시 누르면 빠짐 | 통합 |
| 13 | 뒤로·앞으로 가기로 필터 복원 | E2E |
| 14 | 새로고침해도 필터 상태 유지 | E2E |
| 15 | 목록 진입 → 담기 → 헤더 확인 | E2E |

이 중에서 결정하는 데 오래 걸린 부분은 두 개 있었다.

**1번: 장바구니·위시리스트 개수 파생을 단위로 볼지 통합으로 볼지.** 결국 단위로 정했다. 개수는 store 상태에서 순수 계산으로 나오는 규칙이다. 같은 상품을 중복으로 담으면 1로 접히고, 토글로 빼면 원래대로 돌아온다. 입력에서 출력만 보면 되니 단위로 충분하고, 배지를 실제로 렌더해서 보는 경로는 어차피 12번(담기 → 헤더 숫자)·15번(목록 → 담기 → 헤더)이 통합·E2E로 커버한다. 만약 통합으로 올렸다면 hydration 전 placeholder에서 복원 후 실제 개수로 바뀌는 것까지 사용자 관점으로 볼 수 있었겠지만, 그건 개수 파생보다 넓은 범위라 12·15와 겹친다고 생각했다.

**11번: "조작이 URL에 반영되고 그 URL로 재진입하면 복원되는가"를 통합과 E2E 중 어디에 둘지.** E2E 하나로 통일했다. URL 반영만 다른 테스트로 떼면 jsdom 통합에서도 빠르게 볼 수 있지 않나? 하고 생각했다. 하지만 "그 URL로 재진입해 복원된다"는 실제 문서 로드라야 믿을 수 있고, 조작 → URL 반영 → 재진입은 사용자의 한 연속 흐름이다. 반영을 통합으로 따로 떼면 E2E 재진입 테스트에서 그 반영 단계가 중복되고, 어디까지가 통합이고 어디부터가 E2E인지 경계도 흐려진다. 반영을 통합으로 쪼갰다면 E2E 부담은 조금 덜었겠지만, 한 검증을 jsdom과 실제 브라우저로 따로 보는 셈이라 신빙성이 떨어진다고 생각했다.

### "다음엔 하면 좋겠다" 싶었던 부분 
홈 → 목록 prefetch로 이어지는 초기 진입 통합 테스트가 있으면 좋겠다고 생각했다. 홈에서 만든 prefetch key가 목록 페이지의 조회 조건과 일치해야 "클릭 즉시 캐시 hit"가 성립하는데, 어긋나면 초기 진입에서 중복 요청이 조용히 난다. 

### "앞으로도 안 하겠다" 싶었던 부분
색상·`className` 같은 표현 세부 테스트를 넣지 않게 앞으로도 조심해야겠다고 생각했다. 단순 색상 스타일 같은 게 아닌 사이즈나 position처럼 사용자 동작에도 영향을 미칠 수도 있는 경우도 있겠지만 정말로 이런 테스트가 필요하다면 스냅샷 테스트를 도입해 보는 게 좋을 것 같다고 생각했다.

## 2단계: 정한 대로 구현하기

통합과 E2E의 역할은 "전체 사용자 플로우인가?"를 기준으로 구분하려고 했다. 컴포넌트·상태·네트워크가 얽힌 "이걸 하면 이게 보인다"는 한 화면 안의 반응이라 통합으로도 충분하다 판단했다. 반대로 여러 화면과 내비게이션을 거치는 전체 여정은 E2E로 뺐다. 필터가 주소창에 실리고 그 URL로 다시 들어가 복원되는지, 뒤로/앞으로 가기로 상태가 돌아오는지, 새로고침해도 유지되는지, 목록 진입부터 담기까지 한 흐름이 끝까지 이어지는지가 그랬다.

이걸 기준으로 삼아 1단계에서 정한 15개의 케이스에 대한 구현은 AI에게 맡기고 리뷰는 내가 하는 방식으로 진행하였다. 그 과정에서 내가 발견한 특이 사항은 다음과 같았다.

- 2단계에서 마크업엔 `data-testid`를 하나도 두지 않게 변경하였다. 원래 배지에 있던 `cart-count`도 role·이름으로 바꾸며 없앴다. `getByTestId`는 딱 한 곳, `commerceState.contract.test.tsx`의 "같은 상품을 여러 곳에 그려도 한 곳에서 담으면 다른 곳 버튼·헤더가 함께 바뀐다" 테스트에서만 썼다. 그것도 **테스트가 직접 만든 wrapper** `<div data-testid="home-surface">`·`<div data-testid="list-surface">`에만. 이 두 wrapper는 실제 앱에서 홈(`/`)과 목록(`/products`), 즉 서로 다른 Next.js 페이지(`page.tsx`)를 대신해 만든 wrapper다. 진짜 앱에선 둘이 별개 라우트라 한 화면에 같이 뜰 일이 없지만 테스트를 위해 `home-surface`(홈의 `page.tsx`)와 `list-surface`(상품 목록의 `page.tsx`)로 나누어 각각의 surface 안에 컴포넌트를 넣어 테스트하였다.
  - AI가 테스트 안에서 testid를 쓴 결정을 수용할지 많이 고민했다. testid를 안 쓰겠다고 page.tsx에 wrapper를 달고 거기에 `role`이나 `aria-label`을 붙이면, 실제 사이트엔 없는 의미를 테스트를 위해 지어내는 것이다. 그래서 검증 대상 컴포넌트는 손대지 않고, 테스트 자신의 스캐폴딩인 wrapper div에만 testid를 붙였다.

![실제 앱의 서로 다른 라우트인 app/page.tsx와 app/products/page.tsx에서 각각 사용하는 장바구니 버튼 컴포넌트를 계약 테스트의 home-surface와 list-surface wrapper 안에 함께 렌더해 동시에 검증하는 구조](/week8-frontend-testing-strategy/page-tsx-to-test-wrappers.png)

- `toHaveValue("fashion")`으로 단언한 코드가 있었는데, select의 `value`는 URL·폼에 쓰이는 값이지 사용자가 보는 값이 아니다. 사용자가 보는 `option:checked`의 `toHaveText("패션")`으로 바꿔야 맞다고 판단하여 수정하였다.


## 3단계: 일부러 망가뜨려서 검증하기(뮤테이션 테스트)

3단계는 내가 쓴 테스트가 진짜로 뭘 지키는지 확인하는 단계였다. 15개 검증 대상마다 구현 한 곳을 조건 뒤집기·호출 삭제·경계 부호 변경과 같은 방법으로 망가뜨리고 테스트 코드는 건드리지 않았다. 방법론별로 최소 하나씩은 채웠다. 이 실험은 직접 손으로 했다.

직접 해본 결과 13개는 예상대로 잡혔고, 나머지 두 개는 망가뜨렸는데도 통과했다. 다만 성격이 달랐다. 8번은 진짜 false positive였다. 하지만 7번은 확인해 보니 있으나 마나 똑같은 데드코드였다.

| # | 망가뜨린 곳 | 어떻게 | 왜 못 잡았나 | 대응 |
| --- | --- | --- | --- | --- |
| 7 | `error.tsx`의 `resetQueries` | 호출 제거 | 애초에 있으나 마나인 데드코드 | 테스트가 아니라 코드를 제거 |
| 8 | `useProductListSearchParams.ts`의 `setFilter` | `page: FIRST_PAGE` 제거 | 테스트가 `?page=1`에서 시작해 공백 | page 2에서 시작하는 테스트 추가 |

**7번은 특히나 예상치 못한 결과였다.** `error.tsx`의 재시도 로직에서 `resetQueries` 호출을 지웠는데도 재시도 테스트가 안 깨졌다. 처음엔 테스트가 허술한 줄 알았다. 그런데 실제로 확인해 보니, 에러 경계가 감싼 하위 트리를 `reset()`이 remount할 때 새 `useQuery` observer가 데이터 없는 쿼리에 붙으면서 staleTime이나 refetchOnMount와 무관하게 재요청이 강제되고 있었다. 즉 `resetQueries`는 복구에 아무 기여도 안 하는 데드코드였다. 잘못은 오히려 코드에 있었다. 그래서 테스트를 고치는 게 아니라 데드코드를 제거했다. 살아남은 변형이 항상 테스트 구멍을 뜻하는 건 아니라는 걸 느꼈다.

**8번은 반대로 진짜 테스트 공백이었다.** "카테고리를 바꾸면 1페이지로 리셋된다"는 계약인데, 카테고리를 변경할 때도 호출되는 `setFilter`에서 `page: FIRST_PAGE`를 지워도 기존 8번 테스트가 통과했다. 이유는 그 테스트가 `?page=1`에서 시작했기 때문이다. 이미 1페이지이다 보니 1페이지로 리셋해봐야 결과가 같으니, 리셋 로직이 사라져도 티가 안 났던 부분이었다. page 2에서 시작해 리셋을 정확히 조준하는 테스트를 따로 붙였다. 이번엔 테스트를 고치는 게 맞는 대응이었다.

## Advanced: 뮤테이션 테스트를 자동화 (Stryker)

다음으로는 Stryker라는 툴을 이용해 돌려봤다. Stryker로 뮤테이션 테스트를 했는데, 변형 대상은 과제의 조언대로 단위로 분류한 테스트에 해당하는 코드에만 적용했다. Stryker 설정 자체는 AI에게 맡겼고, 살아남은 변형을 보강할지 말지는 리포트를 보며 AI와 상의해 정했다.

하지만, 문득 왜 통합을 빼야 하는지가 궁금해져서 직접 수치를 재보았고 그제야 이해했다. 시험 삼아 통합 테스트가 걸리는 파일 딱 1개만 대상에 넣어봤더니, 파일 수는 단위 4개의 1/4인데 실행 시간은 16초에서 29초로 거의 2배가 됐다.

| 대상 | 파일 수 | 변형당 다시 도는 테스트 | 실행 시간 |
| --- | --- | --- | --- |
| 단위 | 4 | 1.41개 | 16초 |
| 통합 | 1 | 8.28개 | 29초 |

이 차이는 도구가 도는 방식 때문이었다. Stryker는 소스를 한 곳씩 바꾼 변형을 수백 개 만들고, 변형 하나마다 그 줄을 지나는 테스트를 다시 돌려 잡히는지 본다. 그래서 전체 시간은 대략 `(변형 개수) × (변형당 다시 도는 테스트 수) × (테스트 하나의 실행 시간)`이다. 단위 순수 함수는 한 줄을 대개 한두 테스트만 지나가지만, 통합 컴포넌트는 로딩·빈 결과·에러·정렬 같은 여러 테스트가 렌더하며 같은 줄을 공통으로 지난다. 그래서 변형당 다시 도는 테스트가 1.41개에서 8.28개로 뛴다. 게다가 테스트 하나가 단위는 순수 함수 호출이라 마이크로초면 끝나는데, 통합은 jsdom 렌더 + MSW 왕복도 포함하니 큰 차이가 났다. 두 배율이 곱해지니 대상이 커질수록 금방 감당하지 못할 시간이 걸릴 거라는 게 쉽게 예상됐다. 통합을 넣으면 왜 이렇게 오래 걸리는지에 대한 검증과 이해에 AI를 이용하여 조사했던 게 큰 도움이 됐다.

단위 4파일 전체는 변형 133개(killed 104 · survived 8 · no-coverage 21)에 16초가 걸렸다. 살아남은 8개는 하나씩 다 판정했는데, 보강한 테스트는 0개다. 8개가 전부 죽일 수 없거나 죽여선 안 되는 것들이라고 판단했기 때문이었다. 가장 대표적인 게 `createIdSetStore`의 방어 가드 5개다. 이 store는 담긴 상품 id 집합(`ids`)을 localStorage에 저장했다가 새로고침 때 되살리는데, 저장값이 깨져 있어도 앱이 안 터지게 걸러 주는 가드가 두 개 있다.

```ts
type IdSetStore = {
  ids: Set<string>; // 담긴 상품 id들. 이 개수가 곧 장바구니·위시리스트 배지 숫자
  hasHydrated: boolean; // localStorage 복원이 끝났는지
  // ...
};

// 저장값이 객체인지 확인하는 가드
function isRecord(value: unknown): value is Record<string, unknown> {
  return typeof value === "object" && value !== null;
}
// 저장값에서 문자열 id만 남기는 가드. 손상·구버전 값을 빈 목록으로 안전 복구한다
function toIdArray(value: unknown): string[] {
  if (!Array.isArray(value)) return [];
  return value.filter((item): item is string => typeof item === "string");
}

export function createIdSetStore(storageKey: string) {
  return create<IdSetStore>()(
    persist(
      (set) => ({ ids: new Set(), hasHydrated: false /* ... */ }),
      {
        // Set은 JSON으로 저장이 안 되니 저장할 땐 배열로 바꾼다.
        // 그래서 localStorage에는 { ids: ["p1", "p2"] } 같은 모양으로 들어간다.
        partialize: (state) => ({ ids: [...state.ids] }),
        // 복원할 땐 반대로 배열을 다시 Set으로. 이때 위 두 가드가 손상값을 걸러낸다.
        merge: (persisted, current) => {
          const state = isRecord(persisted) ? persisted : {};
          return { ...current, ids: new Set(toIdArray(state.ids)) };
        },
        // storage, skipHydration 등 생략
      },
    ),
  );
}
```

Stryker는 이 가드들에 대해 뮤테이션 테스트를 한다. 예를 들면 `isRecord`를 항상 `true`로, `toIdArray`의 배열 체크를 `if (false)`로 바꾸는 식이다. 그러면 손상된 저장값(예: `{ ids: "corrupted" }`)이 걸러지지 않고 그대로 `merge`로 흘러 복원 중 예외가 난다. 그런데 이 예외는 내가 따로 잡는 게 아니라 zustand persist가 알아서 처리한다. persist는 복원(rehydrate) 과정을 자체적으로 try/catch로 감싸고 있어서, 예외가 나면 밖으로 던지지 않고 조용히 삼킨 뒤 store를 초기 상태(빈 Set) 그대로 둔다. 결국 가드가 있어서 정상적으로 빈 목록이 되든, 가드가 없어서 예외가 난 뒤 빈 목록이 되든, 겉으로 보이는 값은 똑같다. 죽이려면 "내부에서 예외가 났다 삼켜졌나"를 봐야 하는데 그건 사용자가 보는 게 아니라 구현 세부라고 판단했다.

`apiError`의 `.name` 2개도 비슷하다. 두 에러 클래스가 생성될 때 `this.name`에 이름표를 붙였는데, 이건 로그나 스택 트레이스에서 어떤 에러인지 알아보기 편하라고 붙인 것이다. 정작 에러를 분류하는 `isServerError`는 이 값을 읽지 않는다.

```ts
export class HttpError extends Error {
  constructor(readonly status: number, message: string) {
    super(message);
    this.name = "HttpError"; // 로그용 라벨. Stryker가 "" 로 바꾸는 자리
  }
}
export class NetworkError extends Error {
  constructor(message: string) {
    super(message);
    this.name = "NetworkError"; // 여기도 "" 로 바뀐다
  }
}

// 에러 분류는 .name이 아니라 instanceof와 status로만 갈린다.
// 그래서 .name을 "" 로 바꿔도 어떤 분기도 달라지지 않는다.
export function isServerError(error: unknown): boolean {
  if (error instanceof NetworkError) return true;
  return error instanceof HttpError && error.status >= 500;
}
```

죽이려면 `err.name`을 직접 단언해야 하는데, 그건 사용자 동작이 아니라 로그용 이름표를 검사하는 구현 세부라 넣지 않았다.

`productListMetadata`의 상수 1개는 조금 다른 이유다. 이 값은 함수 안이 아니라 모듈 최상위에 있어서, 파일이 로드될 때 딱 한 번 정해진다.

```ts
// 모듈이 로드될 때 딱 한 번 정해지는 최상위 상수
const ALL_CATEGORY_LABEL = "전체"; // Stryker가 "" 로 바꾸는 자리

function resolveCategoryLabel(query, categories): string {
  if (query.category === "all") return ALL_CATEGORY_LABEL;
  // ...
}
// resolveCategoryLabel은 buildProductListMetadata(서버 메타데이터 조립)에서만 쓰인다.
```

문제는 이게 특정 테스트가 실행되는 도중이 아니라 모듈이 처음 로드될 때 한 번 값이 박힌다는 점이다. 그래서 Stryker가 "이 변형은 어느 테스트가 덮는가"를 특정하지 못하고, 게다가 이 상수를 쓰는 `resolveCategoryLabel`은 1단계에서 단위로 잡은 범위(순수 title 함수) 밖이라 애초에 단위 테스트가 지나가지도 않는다. 그래서 어느 테스트에도 묶이지 않은 채 살아남았다. 

이건 Stryker 문서가 [static mutant](https://stryker-mutator.io/docs/mutation-testing-elements/static-mutants/)로 설명하는 상황과 같다. 변형이 테스트가 도는 중이 아니라 앱이 로드되는 startup 때 한 번 실행되는 값이라(*"executed once on startup instead of when the tests are running"*), 테스트별로 변형을 켜고 끄는 방식이 안 통하고(*"activating or de-activating the mutant won't help"*), 결국 어느 테스트가 이 변형을 덮는지를 도구가 특정하지 못한다. 즉 문서에서 설명한 케이스 처럼 도구가 애초에 특정 테스트에 묶을 수 없는 종류의 변형이기 때문이다. 그래서 이 하나를 죽이겠다고 억지로 테스트를 만들 이유는 없다고 판단했다.

과제 요구사항의 "살아남은 변형 중 의미 있는 것 2개 이상을 골라 테스트를 보강"이 있었지만 이를 채우려고 구현 세부에 대한 테스트를 쓰는 건 주객전도라 판단하여 수정하지 않았다.

### 이 도구를 상시로 쓸까?

나의 판단은 **상시로 사용하지 않는 것이다.** 비용이 대상 규모에 따라 빠르게 커져서 순수 로직 몇 파일만 더 넣어도 16초가 금방 몇 분대로 오를 것으로 보였다. 점수를 merge를 허용·불허하는 게이트로 걸기도 애매했다. 위에서 8개의 검출 사항을 수정하지 않은 케이스도 있다 보니 어디까지를 허용할지의 기준이 애매하다고 느꼈기 때문이다. 게이트로 걸면 통과시키려고 구현 세부에 대한 테스트를 쓰게 된다. 

**만약 붙인다면**: CI에서 자동 실행해 PR 코멘트로 띄우되 머지는 막지 않는 참고용 리포트로 두는 정도가 맞겠다 싶었다. 다만 손으로 못 본 자리를 기계가 드러내 준 건 있었다. `buildProductListMetadata`라는 함수가 단위로 통째로 미커버라는 걸 리포트로 알게 됐는데, 그 출력(description·OG 이미지)은 크롤러와 SNS가 실제로 읽는 값이라 커버리지와 무관하게 테스트를 구현할 가치는 있어 보였다.

## 후기

솔직히 아직 감이 잘 안 잡힌 부분도 있다. 2단계에서 각 항목에 경계 케이스를 함께 넣긴 했는데, "경계"라는 개념 자체가 내 안에서 아직 또렷하지 않다. 어디까지가 정상이고 어디부터가 경계인지, 그 선을 긋는 감각이 부족하다는 느낌이 든다. 경계 케이스를 고를 때 다들 어떤 기준을 쓰는지 궁금하다. 테스트가 살아남았을 때 코드를 지울지 테스트를 더할지, 그 판단은 또 어떻게 가르는지도.

이번 과제를 하며 좋았던 점은 테스트를 구현하기 전에 "무엇을 왜 지키기로 했는지 적어라"를 실천하여 그 덕에 일단 AI에게 만들어 달라고 하기 전에 스스로 생각해보면서 판단력을 키운 부분이었다. 그리고 구현한 내용을 리뷰하며 살아남은 변형이 코드가 죽었다는 신호일 수도 테스트가 비었다는 신호일 수도 있다는 것, 뮤테이션 점수 100%를 목적으로 삼으면 오히려 구현 세부 테스트를 만들게 될 수도 있다는 것도 알게 되었다.
